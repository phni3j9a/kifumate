# 戦法・囲いの自動分類

Issue [#10](https://github.com/phni3j9a/kifumate/issues/10)、仕様 §4 の**判定ロジックのみ**。画面・DB・集計・手動修正の実装は含まない。`tsshogi` 以外の依存は追加していない。

## 呼び出し方

```ts
import {
  classifyRecord,
  classifyMoves,
  classificationCatalog,
} from "../core/classify";

const result = classifyRecord(record); // tsshogi の Record / ImmutableRecord
const alternative = classifyMoves(startPosition, moves); // ImmutablePosition と readonly Move[]
```

- `classifyRecord` は現在表示している手数・選択中の分岐によらず、開始から**本譜**（各ノードの `next`、先頭の兄弟）を終局まで走査する。Record、コメント、分岐選択、開始局面、Move は変更しない。
- 分岐や途中までだけを調べるときは、呼び出し側でその開始局面・通常手列を `classifyMoves` に渡す。
- 開始局面も判定する。`ply: 0` が開始局面で、以降は**入力からの半手数**。後手番開始でも1ずつ増え、SFENの手数欄とは独立。終局理由は半手数に含めない。
- 両玉が必要。指し手の色・駒種・捕獲情報を局面から再生成した Move と照合し、`tsshogi` で合法性も確認する。不正な手や両玉のない局面は例外にする。例外時に部分結果を返さない。

### 戻り値

すべてJSONとして保存可能。

| フィールド                        | 意味                                                                             |
| --------------------------------- | -------------------------------------------------------------------------------- |
| `rulesVersion`                    | 判定規則の版。現在は `1`                                                         |
| `processedPlies`                  | 読み取った通常手数                                                               |
| `sides.black` / `sides.white`     | 先手／後手ごとの分類                                                             |
| 各側の `family`                   | 最後に確定できた `居飛車` / `振り飛車`。一度も確定しなければ `未分類`            |
| `familyHistory`                   | 大分類が変わった順のイベント。形が崩れて不明になっても、以前の確定情報を消さない |
| `strategies`                      | 具体的戦法・派生形の**初回成立**順。各IDは一局・片側につき一回                   |
| `castles`                         | 完成した囲いの成立順。形の継続は重複せず、崩して再建した場合は同じIDも再登場する |
| `strategyStatus` / `castleStatus` | 対応配列が空なら `未分類`、成立イベントがあれば `判定済み`                       |
| `relationships`                   | 両側の大分類から確定した対局全体の戦型。関係が変われば追記                       |
| `relationshipStatus`              | 関係が一度も確定しなければ `未分類`                                              |

戦法・囲い・対局戦型の各イベントは `id`, `name`, `ply`, `sfen`, `conditions` を持つ。`conditions` は確認した駒の位置や交換履歴などの日本語の根拠。大分類イベントはIDの代わりに `family` を持つ。駒位置の数字は筋・段の順（例: `28` は２八）。駒配置の根拠は盤上の実座標、大分類の説明中の座標は先手側へ正規化した座標。

囲いにはカタログ上の `parentId` が付く。さらに、その親を入力内で実際に観測した場合だけ `evolvesFromPly` を付け、直近の親イベントの手数を示す。銀冠の局面から入力した場合は、高美濃・美濃のイベントを捏造しない。

```text
美濃囲い    ply:17
高美濃      ply:23  parentId:mino       evolvesFromPly:17
銀冠        ply:29  parentId:high-mino  evolvesFromPly:23
```

これは対局中の**観測履歴**であり、終局図の現在形や形の有効期間を返すAPIではない。最後の囲いも終局まで残存したことは保証しない。

## 対応する種類

モック `ST_MASTER` / `CS_MASTER` / `CS_PARENT` の全種類に対応。公開カタログは `classificationCatalog`、規則の実体は `src/core/classify/rules.ts`。

### 戦法（18種類）

| 分類               | 対応戦法                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------- |
| 居飛車系           | 矢倉、角換わり、相掛かり、横歩取り、雁木、棒銀、右四間飛車、対四間飛車急戦、対振り持久戦 |
| 振り飛車系         | 四間飛車、三間飛車、中飛車、向かい飛車、相振り飛車                                       |
| 追加の戦法・派生形 | 袖飛車、早繰り銀、腰掛け銀、角交換振り飛車                                               |

相振り飛車は両者の関係を表すため、双方の戦法と `relationships` の両方に記録する。角換わり・相掛かり・横歩取りも双方へ記録する。角交換振り飛車は実際に振った側だけへ記録する。

### 囲い（11種類）

美濃囲い、高美濃、銀冠、舟囲い、エルモ囲い、金矢倉、雁木囲い、左美濃、居飛車穴熊、振り飛車穴熊、中住まい。

発展関係は `美濃囲い → 高美濃 → 銀冠`。それ以外の囲いの移行は観測した順序だけを記録し、根拠のない親子関係を追加しない。

### 対局全体

相居飛車、対抗形、相振り飛車。両側の大分類が同じ局面で確認できたときだけ記録する。

### 公開しない種類

ゴキゲン中飛車、石田流、ミレニアム、木村美濃、片美濃、ダイヤモンド美濃、菊水矢倉、天守閣美濃などは、専用の合法手順・近似形の反例をまだ用意していないため、専用ラベルを公開しない。中飛車など上位の形が確認できた場合は上位だけを返し、上位も不明なら未分類にする。

## 判定方式

1. 開始局面を複製し、通常手を一手ずつ合法性確認・適用する。
2. 後手の位置を180度回転し、先手と共通の駒配置表で照合する。
3. 大分類は**飛車の筋だけでは確定しない**。自陣6〜9段目の飛車と7〜9段目の玉を確認し、飛車と玉が逆側にある配置を要求する。居飛車は飛車2〜4筋・玉6〜9筋、振り飛車は飛車5〜8筋・玉1〜4筋。中央の玉58/59でも、飛車2筋・金78・飛車先の歩25/26または飛車26の組み合わせなら居飛車とする。飛車が前進・成った場合は、過去に確定した大分類だけを維持する（攻めた飛車の筋で新しく分類し直さない）。飛車・龍が複数ある局面は新しく確定しない。
4. 各規則に書いた要所の駒が**すべて**一致する場合だけ、その形を成立とする。例えば右四間は飛車48・銀56/45・歩46、四間は飛車68・歩66。袖飛車は飛車38・歩36、三間は飛車78・歩76で、玉の側も異なる。
5. 矢倉・雁木は今回、完成した金矢倉・雁木囲いも確認できる形に限定する。舟囲いは玉78・金58/69・銀79、エルモ囲いは玉78・銀68・金79/59を要求し、玉と金を取り違えない。
6. 双方の大分類が確定してから対局全体や相手依存の規則を適用する。対四間飛車急戦は相手の四間形と、自分の玉78・金58・銀46・歩36・角88を要求する。対振り持久戦は相手の振り飛車と、自分の左美濃か居飛車穴熊の完成を要求する。早繰り銀は飛車28・銀46/79・歩36/25、腰掛け銀は飛車28・銀56・歩57/46を相居飛車で要求する。
7. 交換系の戦型には手順の証拠も要求する。**入力の32手以内**に、角換わり／角交換振り飛車は初期角位置22/88での角による角取りと直後の同地点での取り返し、相掛かりは双方の飛車先の歩を飛車で取った履歴と双方未開通の角道、横歩取りは双方の飛車先交換の後で飛車24→34によって横歩を取った履歴を確認する。相掛かり・横歩取りでは双方の角が初期位置に残っていることも要求する。

数値の確信度や機械学習、棋譜の戦型ヘッダー、曖昧な候補の推測は使用しない。

## 既知の限界

- **誤判定回避のため取りこぼす設計**。同じ名前でも金の一枚違い、玉の位置違い、早い仕掛け、銀冠の別形などは拾わない。未完成の囲いから完成形を先読みしない。
- 大分類にも玉の移動を要求するため、飛車を振った直後や居玉の序盤は未分類になり得る。相手依存の戦型は相手の形が確認できるまで遅れる。
- 対四間飛車急戦／対振り持久戦は、狙いや持ち時間を推測したものではなく、上記の代表的配置への一致である。急戦と持久戦の全手順を網羅しない。
- 交換系の32手制限は入力開始から数える。32手を超える遅い交換や、取り返しの前に別の手を挟む角交換、角を打ち直した横歩取りは専用名を返さない。途中局面だけでは、それ以前の交換を持ち駒から推測しない。
- 開始局面が途中図・駒落ちでも、両玉と必要な形があれば位置で判定できる。ただし履歴に依存する戦型は渡した通常手列に証拠が必要。局面の由来や物理的に到達可能かまでは検証しない。
- 全手数を走査する。中終盤でも要所が完全一致すれば配置を記録するため、人間による戦法名の付け方と常に一致する保証はない。実戦コーパスでの精度測定は未実施。

## 規則の追加・修正

1. 配置だけで表せるものは `rules.ts` の該当配列へ `{ id, name, family, pieces }` を追加する。例: `[GOLD, 49]` と `[GOLD, 58]` は両方必須、`[KING, 69, 79]` はどちらか一方。規則はデータで書き、汎用DSLや優先順位の機構は増やさない。
2. 囲いの発展形は `parentId` を追加する。実際に親を経由したかどうかは走査処理に任せる。
3. 相手や交換履歴が必要な場合だけ `index.ts` の専用判定を追加する。配置だけで角換わり・相掛かり等を推測しない。
4. `tests/classify.test.ts` に平手からの合法な代表手順を自作し、先手・後手の陽性例と近い陰性例を追加する。生成時も `tsshogi` で合法性を確認する。カタログにだけ名前を追加しない。
5. 意味が変わる修正では `rulesVersion` を更新し、この文書の対応一覧・限界も直す。
6. `cd app && npm run check` を実行する。既存の `tests/*.test.ts` に含まれるため scripts の変更は不要。

## 画面・DBと接続するとき

- エントリーポイントは `src/core/classify/index.ts`。公開型は `Classification`, `SideClassification`, `Finding`, `CastleFinding`, `Evidence`, `Family`。
- `classificationCatalog` のIDで保存・フィルターし、名前で表示する。戦法と囲いで同じID（例: `gangi`）があるため、**種別とIDの組**で扱う。
- 戦法は配列全体を保持する。囲いは履歴配列を保持し、発展は `parentId` と `evolvesFromPly` で表示する。未分類ステータスと空配列を画面に反映する。
- 統計はイベント行の件数ではなく**対局IDの重複を除いて**数える。同じ囲いを築き直す場合や複数の戦法・大分類を経由する場合がある。大分類の絞り込みを「最終確認」か「一度でも観測」かは集計側で明示する。
- `family` は最後に確認された大分類。履歴が必要なら `familyHistory` を使う。終局時の配置そのものを表示したい場合、この履歴APIの最後のイベントを現在形と断定しない。
- `rulesVersion` と元棋譜を残せば再判定できる。手動修正は自動結果と分けて保存し、再判定で上書きしない。手動修正UI／DBマイグレーションは本変更に含まれない。

## 検証

`tests/classify.test.ts` の36テストで、公開全18戦法・11囲いの合法手順、先後、発展の手数と親、途中図、飛車の転換、大分類・対局関係の転換、再建、紛らわしい形、未分類、非合法入力、履歴がない角交換、32手制限、本譜と分岐の分離、入力非破壊を確認する。将棋エンジンの評価値・勝率やUI表示は検証対象外。

配置の確認時には、[居飛車と振り飛車（居飛車編）](https://www.jti.co.jp/culture/shogi/guide/08/index.html)、[エルモ囲い](https://shogigame.org/learn/castles/elmo)、[美濃系の基本形](https://shoginote.com/castles/mino) も参照した。テスト棋譜は外部棋譜・別プロジェクトからの転載ではない。
